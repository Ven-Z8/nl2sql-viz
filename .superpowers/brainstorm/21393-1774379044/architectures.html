3 Architecture Approaches for NL2SQL + Real-Time Viz

Which foundation fits best? Consider: speed to MVP, scalability, complexity.

A

Layered Monolith

FastAPI + Claude Agent SDK + BUN sidecar

One app, multi-agent coordination inside it. Coordinator agent calls sub-agents (Schema, SQL, Code Exec, Viz) as tools. WebSockets stream results to browser. BUN runs as a local subprocess for code execution.

Pros

  • Fast to build — working in days
  • Easy to debug — everything in one place
  • Clean agent boundaries from day one

Cons

  • Harder to scale BUN execution independently
  • Real-time streaming needs careful async design

⭐ Recommended for Phase 1 — architect with clean service interfaces so components can be extracted later

B

Service-Oriented Agent Mesh

Separate microservices + Redis/message queue + Claude Agent SDK across services

Connector Service, Agent Orchestration Service, BUN Execution Service, Viz Service — each independently deployable. Claude Agent SDK orchestrates across service boundaries via message queues.

Pros

  • Scale BUN execution independently (CPU-intensive)
  • Fault isolation per service
  • Enterprise-ready from the start

Cons

  • 2-3× more complex to build initially
  • More infra to manage (queues, service discovery)
  • Harder to debug distributed flows
C

Event-Driven Data Platform

Kafka/CDC data layer + Agent layer + Viz layer as distinct tiers

Three fully separate tiers: (1) Data ingestion tier with Kafka/CDC/schedulers feeding a time-series store. (2) Agent tier where Claude analyzes data via NL. (3) Viz tier with BUN + Vega-Lite rendering to live dashboards.

Pros

  • True production-grade real-time at scale
  • Horizontal scaling per tier
  • Cleanest architecture long-term

Cons

  • Weeks to months just to bootstrap
  • Significant infra: Kafka, time-series DB, etc.
  • Overkill until you have real traffic
